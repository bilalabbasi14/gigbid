# Adaptive Learning Platform — 2024 | Education  

## Context  
The client was a mid‑size tutoring agency that delivers one‑on‑one and group sessions across K‑12 subjects. Their existing LMS was static: every student received the same set of exercises regardless of mastery level, leading to disengagement and high churn. They approached us in early 2024 to build a modern web application that could dynamically adapt content difficulty based on real‑time performance data, while also supporting secure multi‑role access (students, tutors, admins) and seamless scalability for a projected 15 k concurrent users during peak enrollment periods.

## Challenge  
Key hurdles included:  

* **Adaptive algorithm integration** – the platform needed a reliable engine that could recompute difficulty after each quiz submission without adding noticeable latency.  
* **Secure, frictionless authentication** – students often signed in from mobile browsers; the agency required social logins plus email/password, with role‑based permissions.  
* **Maintainable data layer** – the tutoring content hierarchy (courses → modules → lessons → questions) demanded a flexible schema that could evolve as new subjects were added.  
* **Rapid delivery** – the contract stipulated an 18‑week timeline, leaving little room for extensive re‑work.  

## Approach  
I served as Lead Full‑stack Engineer, assembling a cross‑functional squad of two front‑end developers, one data scientist, and a QA specialist. We adopted an **agile sprint cadence** (2‑week sprints) with continuous integration via GitHub Actions.  

1. **Architecture** – Chose **Next.js** with **SSR** for SEO‑friendly landing pages and fast first‑paint, while leveraging **API routes** for the adaptive engine.  
2. **Authentication** – Integrated **next‑auth** with Google OAuth and email/password, configuring JWT sessions and role‑based callbacks.  
3. **Data modeling** – Used **Prisma** as the ORM over **PostgreSQL**, defining a normalized schema that captured student attempts, difficulty scores, and content metadata.  
4. **Adaptive engine** – Implemented a Bayesian Knowledge Tracing model in a separate Node service, invoked from the Next.js API route on each quiz submit; results were persisted via Prisma.  
5. **Styling & UI** – Built a responsive UI with **Tailwind CSS** and **react‑hook‑form** for performant form handling.  
6. **DevOps** – Containerized the app with **Docker**, orchestrated with Docker Compose for local dev and deployed to AWS ECS. CI pipelines ran **ESLint**, **Prettier**, and unit tests on every PR.

## Results  
* **Student progression speed ↑ 27 %** – average time to move from “Beginner” to “Intermediate” dropped from 4.2 weeks to 3.1 weeks, measured via cohort analytics.  
* **Retention rate ↑ 14 pp** – month‑over‑month retention climbed from 68 % to 82 % after the first quarter post‑launch.  
* **Performance** – 99.8 % of quiz submissions processed under 200 ms; peak concurrent load of 12 k users sustained with <1 s response time.  
* **Developer velocity** – weekly PR throughput averaged 12 PRs with a 92 % first‑time pass rate on CI checks.  

## What I Would Do Differently  
If I were to start this project again, I would **introduce GraphQL** (Apollo Server) for the content queries. While REST‑style API routes served the MVP well, the evolving content hierarchy soon required more granular fetching, and GraphQL would have reduced over‑fetching and simplified client caching. Additionally, I would **prototype the adaptive engine as a serverless function** (AWS Lambda) earlier in the timeline to benefit from automatic scaling and lower operational overhead, especially during enrollment spikes. Finally, investing a week in **UX research with actual students** before finalizing the UI would have uncovered a few minor accessibility issues (color contrast on low‑vision devices) that we later patched post‑launch.
