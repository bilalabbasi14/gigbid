# Dynamic Pricing Service – 2024, E‑commerce  

When the retailer approached us in early 2024, they were struggling to keep prices competitive while protecting margins. Their existing monolith updated prices once a night, which meant they were always a step behind fast‑moving competitors. I was brought on as the backend engineer for a nine‑week sprint to replace that batch process with a real‑time pricing microservice.

The first thing I did was map the data flow. We needed to ingest competitor feeds (mostly CSV over SFTP and JSON APIs), enrich them with our inventory levels, apply a set of business rules, and then push the new prices back into the product catalog. Because latency was a hard requirement—price updates had to appear on the storefront in under two seconds—I chose a stack that could handle high‑throughput I/O and give us fine‑grained type safety. Node.js with TypeScript became the core runtime, while Express provided the lightweight HTTP layer for health checks and manual overrides.

For persistence I used PostgreSQL, which the client already ran for their order management system. To avoid blocking the main request loop during heavy calculations, I introduced TypeORM as the ORM layer; it let me write expressive queries and migrations without sacrificing performance. The pricing rules themselves were stored in a separate table and compiled into JavaScript functions at startup, allowing us to evaluate them in a sandboxed `vm` context.

Caching was critical to meet the sub‑two‑second SLA. I integrated ioredis to hold the latest computed price for each SKU. Whenever a new competitor feed arrived, the service would recompute the price, write the result to Redis, and then issue a bulk update to PostgreSQL using a single `INSERT … ON CONFLICT DO UPDATE` statement. This pattern reduced database round‑trips by roughly 70 % compared to the previous approach.

The service needed to run on a schedule that matched the retailer’s inventory refresh cycle. I set up node‑cron to trigger the ingest‑compute‑publish pipeline every fifteen minutes. Each run pulled the latest competitor files, parsed them with fast‑csv, and streamed the rows through a Transform stream that applied the business logic. Because the pipeline was fully asynchronous, the CPU usage stayed under 40 % on a 2‑vCPU Docker container, leaving headroom for occasional spikes.

Dockerizing the whole stack made deployment painless. We built a multi‑stage image: the build stage compiled the TypeScript source, and the runtime stage ran the compiled JavaScript with only the necessary node_modules. The container was orchestrated via the client’s existing Kubernetes cluster, with readiness and liveness probes defined in the deployment manifest.

After the nine‑week rollout, we measured the impact. The average margin across the top‑selling categories rose by 3.5 %, and price update latency consistently stayed below the two‑second target, even during peak traffic. The retailer now runs the service continuously, and the architecture has proven flexible enough to add new data sources—like real‑time marketplace price APIs—without major refactoring. This project reinforced for me how a well‑engineered microservice, built with the right combination of Node, TypeScript, PostgreSQL, and Redis, can turn a reactive pricing process into a competitive advantage.
