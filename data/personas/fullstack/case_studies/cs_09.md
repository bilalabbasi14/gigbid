# Production Line KPI Dashboard – 2022 | Manufacturing  

**Project ID:** p09  
**Role:** Backend Engineer (Full‑stack) – Daniel Okafor  

---  

### Overview  
- **Client:** Enterprise‑level manufacturing firm (multiple plants, >3 000 sensors).  
- **Timeline:** 11 weeks (Jan 10 – Mar 24 2022).  
- **Goal:** Provide real‑time equipment efficiency visibility; replace legacy CSV reports.  

---  

### Key Decisions & Rationale  

- **Tech Stack Selection**  
  - Chose **Node.js** + **Express** for API layer (fast I/O, easy integration with existing Python‑based analytics).  
  - Adopted **GraphQL** via **apollo-server-express** to let front‑end request only needed KPI fields, reducing payload size by ~38 %.  
  - Used **PostgreSQL 13** (native JSONB) for sensor event storage; leveraged materialized views for daily aggregates.  
  - Implemented **Docker** (Compose v2) for reproducible dev/prod environments; each service isolated (api, db, nginx).  

- **Schema Design**  
  - Defined `sensor_readings` table (partitioned by day, ~1.2 M rows/day).  
  - Created `equipment_kpi` materialized view refreshed every 5 min (indexed on `equipment_id`, `timestamp`).  
  - GraphQL schema: `equipment(id): Equipment!`, `kpi(equipmentId, range): [KPI!]!`.  

- **Performance Optimizations**  
  - Added **pgBouncer** connection pooling; reduced average DB latency from 12 ms to 4 ms.  
  - Enabled **Apollo cache‑control** headers; client cache hit rate ~72 % after first load.  
  - Implemented batch loading with **DataLoader** to collapse N+1 queries (average query count per dashboard refresh dropped from 27 to 3).  

- **Security & Compliance**  
  - Enforced JWT auth (HS256) with 15‑minute token expiry; integrated with corporate SSO via OAuth2.  
  - Applied **Helmet** middleware, disabled `x-powered-by`, and enforced CSP.  
  - Conducted quarterly penetration test; no critical findings.  

- **Testing & CI/CD**  
  - Unit tests with **Jest** (coverage 88 %).  
  - End‑to‑end GraphQL tests via **Apollo Server Testing**; 45 test cases covering edge‑case timestamps.  
  - CI pipeline (GitHub Actions) runs lint, test, and builds Docker images; deploys to AWS ECS Fargate on merge to `main`.

### Outcomes  

- **Financial Impact:** Identified three equipment bottlenecks; plant saved **$120 K** in annual downtime (≈ 5 % efficiency gain).  
- **User Adoption:** Dashboard accessed by **85 %** of shift leads within first month; average session length 7 min.  
- **Scalability:** System handles **≈ 2 500 concurrent GraphQL requests** with <200 ms latency (stress test at 3× production load).  
- **Maintainability:** Codebase ~7 k LOC; Docker images <200 MB; documentation covers onboarding in <30 min.  

---  

### Lessons Learned  

- Materialized views proved essential for time‑series aggregation; raw table scans were a performance bottleneck.  
- Early implementation of DataLoader avoided costly N+1 patterns that later surfaced during UI integration.  
- Close coordination with the front‑end team (React + Recharts) ensured GraphQL schema matched visual requirements, reducing re‑work.
