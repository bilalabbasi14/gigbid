# Volunteer Coordination Portal – 2019 | Non‑profit  

**Project ID:** p12 **Role:** Full‑stack Developer (React/Next.js, Node, Django, Postgres)  
**Duration:** 7 weeks **Client:** Individual community organizer  

---  

### Sprint 1 (Week 1) – Foundations & Planning  
- **Kick‑off meeting (02‑Jan‑2019):** clarified scope – event list, volunteer sign‑up, hour tracking, bilingual UI (EN/FR).  
- **Tech stack decision:** Next.js 13 (React 18) + TypeScript for SSR; Supabase for auth + Postgres DB; Tailwind CSS 3.0 for UI; `next‑i18next` for i18n. Chose Supabase over Firebase to keep SQL querying simple and avoid vendor lock‑in.  
- **Repo init:** `git init volunteer‑portal`; set up `main` branch, commit `init: scaffold Next.js with TypeScript`.  
- **CI/CD:** Added GitHub Actions workflow (`node12.yml`) to run `npm run lint` & `npm test` on PRs.  

### Sprint 2 (Week 2) – Auth & Data Model  
- **Supabase project created (15‑Jan‑2019):** enabled Email‑Password auth, row‑level security (RLS).  
- **Database schema:** `volunteers(id UUID PK, name VARCHAR, email UNIQUE, hours INT DEFAULT 0)`, `events(id UUID PK, title VARCHAR, date DATE, capacity INT)`, `registrations(id UUID PK, volunteer_id FK, event_id FK, status ENUM)`.  
- **Commit:** `feat: supabase schema + RLS policies`.  
- **Performance trade‑off:** opted for single table `registrations` instead of many‑to‑many join view to reduce query latency (≈ 30 ms avg on 100 rows).  

### Sprint 3 (Week 3) – Core UI & Internationalisation  
- **Tailwind config:** enabled JIT mode, custom colors `brand-primary:#2C3E50`.  
- **Component library:** built `Button`, `Modal`, `FormInput` using `@headlessui/react`.  
- **i18n:** integrated `next‑i18next`; added locale files (`en.json`, `fr.json`) with 120 keys.  
- **Commit:** `feat: UI components + i18n scaffold`.  

### Sprint 4 (Week 4) – Event Management & Volunteer Dashboard  
- **API layer:** created `/api/events` (GET, POST) using Next.js API routes; leveraged `supabase-js` client for DB ops.  
- **Dashboard:** React hook `useVolunteerHours` aggregates hours via `supabase.from('registrations').select('...')`.  
- **Edge case handling:** prevented double‑booking by checking `capacity` before insertion; added server‑side guard (return 409 Conflict).  
- **Commit:** `fix: capacity check & duplicate registration guard`.  

### Sprint 5 (Week 5) – Testing & Accessibility  
- **Unit tests:** Jest 26 + React Testing Library; 45 tests covering auth flow, event CRUD, registration. Achieved 92 % coverage.  
- **a11y audit:** Lighthouse score 98 / 100; added `aria-label`s to all interactive elements.  
- **Commit:** `test: add coverage for core flows`.  

### Sprint 6 (Week 6) – Performance Optimisation & Deployment  
- **Static generation:** pre‑rendered event list with `getStaticProps`; revalidated every 5 min (ISR).  
- **Bundle analysis:** `webpack-bundle-analyzer` showed 1.8 MB JS payload; trimmed by removing unused lodash functions (↓ 22 %).  
- **Deploy:** Vercel production branch; environment vars for Supabase URL & anon key.  
- **Commit:** `perf: ISR for events + bundle size reduction`.  

### Sprint 7 (Week 7) – Handoff & Metrics Tracking  
- **Documentation:** Markdown `README.md` with setup, env, and contribution guide.  
- **Analytics:** Integrated Plausible (privacy‑first) to track sign‑ups; dashboard shows 102 volunteers in first 90 days.  
- **Outcome:** Volunteer registrations > 100 (first 3 months); event attendance up ≈ 40 % vs. previous manual process.  
- **Final commit:** `chore: release v1.0 – production ready`.  

---  

**Key takeaways:**  
- Supabase + Next.js delivered a full‑stack solution in < 2 months without a separate backend repo.  
- Early RLS policies prevented data leaks, allowing the client to manage permissions via Supabase UI.  
- Tailwind JIT + component abstraction kept CSS bundle < 120 KB, ensuring fast load on low‑bandwidth community networks.
