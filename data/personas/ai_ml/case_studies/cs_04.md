# Real‑Estate Document Analyzer – Phase 2 (2022) – Real Estate  

## Context  
The client, a large enterprise in the real‑estate sector, had already deployed Phase 1 of a document analysis platform that extracted key clauses from lease and purchase contracts. While the extraction pipeline was robust, the legal team struggled to locate similar contracts quickly when reviewing new deals. They needed a semantic search capability that could surface relevant documents from a portfolio of over 30,000 contracts in near‑real time.

## Challenge  
- **Speed:** Existing keyword‑based search returned results in 1–2 seconds, which was too slow for the lawyers’ workflow.  
- **Relevance:** Simple term matching missed semantically similar clauses (e.g., “early termination” vs. “premature exit”).  
- **Scalability:** The solution had to handle continuous ingestion of new contracts without degrading performance.  
- **Integration:** The search service needed to be exposed as a REST API that could be called from the existing FastAPI front‑end used in Phase 1.

## Approach  
1. **Vectorisation Layer:** Leveraged a pre‑trained **sentence‑transformers** model (all‑MiniLM‑L6‑v2) to embed each contract paragraph into a 384‑dimensional vector.  
2. **pgvector Index:** Stored vectors in a **PostgreSQL** database enhanced with the **pgvector** extension, enabling efficient approximate nearest‑neighbour (ANN) queries with IVF‑Flat indexing.  
3. **LangChain Orchestration:** Built a **LangChain** chain that (a) receives a natural‑language query, (b) generates the query embedding, (c) performs a similarity search via pgvector, and (d) ranks results using a lightweight cross‑encoder re‑ranker.  
4. **FastAPI Wrapper:** Exposed the chain through a **FastAPI** endpoint (`/search`) that accepted plain text and returned the top 5 contract snippets with metadata.  
5. **Dockerised Deployment:** Containerised the entire stack (PostgreSQL + pgvector, FastAPI service, and a background worker for batch embeddings) using **Docker Compose**, ensuring reproducible environments across dev, staging, and production.  
6. **MLOps Practices:** Added CI/CD pipelines with **GitHub Actions** to run unit tests, linting, and automated model version bumping. Implemented Prometheus metrics for latency and error rates, and set up alerts for latency >250 ms.

## Results  
- **Search latency:** Average end‑to‑end latency dropped from ~1.2 s (keyword) to **<200 ms** for the top‑5 results, comfortably within the 250 ms SLA.  
- **User satisfaction:** Post‑deployment surveys showed the legal team’s satisfaction score rise from **3.8/5 to 4.6/5**.  
- **Adoption:** Daily query volume increased by 38 % within the first month, indicating higher trust in the semantic search.  
- **Scalability:** The system comfortably handled a 2× increase in document ingestion (≈60 k contracts) without noticeable latency degradation, thanks to pgvector’s ANN indexing.

## What I Would Do Differently  
1. **Hybrid Retrieval:** Combine sparse BM25 retrieval with dense vectors to capture both exact term matches and semantic similarity, which could improve recall for niche legal terminology.  
2. **Rerank Model Optimization:** Replace the cross‑encoder re‑ranker with a distilled model (e.g., MiniLM‑v2‑Distil) to reduce inference time while keeping ranking quality.  
3. **Incremental Embedding Pipeline:** Move the batch embedding step to an async Kafka‑driven pipeline, allowing near‑real‑time updates as contracts are uploaded, rather than nightly batch jobs.  
4. **Fine‑tune Embeddings:** Fine‑tune the sentence‑transformers model on a small, labelled corpus of contract clauses to better capture domain‑specific language, which could further boost relevance scores.
